# Upgrade notes: 1.1.2

The rest of the fixes from the 1.1 audit. Plugin and theme contracts do not change.

```bash
composer update pnscripts/pn-shop-core --with-all-dependencies
php artisan pnshop:update
php artisan optimize && php artisan queue:restart
```

The update adds indexes (on PostgreSQL and SQLite mostly; MySQL already has most of them). On a large shop, run it outside busy hours.

## Behaviour changes

- **Order states in the admin:**
  - *Update payment status* no longer offers "refunded" or "partially refunded"; use *Refund*.
  - *Update fulfillment status* is gone. Use *Create shipment* to ship, and return requests for returned goods.
- **Admin API:**
  - Transitions to refunded, shipped or returned are refused (422). Use `POST /orders/{id}/refunds` and `POST /orders/{id}/shipments`.
- **Refunds:** a refund is saved as *pending* before the payment provider is asked, then becomes *completed* or *failed*. A refund that stays *pending* needs a look at the provider's dashboard.
- **Variants:** the last variant of a product cannot be deleted. Deleting the default variant makes another one the default.
- **API tokens:** staff tokens made in the admin expire after 30, 90 or 365 days. `pnshop:api-token` makes tokens that expire after a year unless `--days` says otherwise. Existing tokens keep their expiry.
- **Plugins:** enabling, disabling, updating or removing a plugin clears cached routes and admin components. Run `php artisan optimize` again afterwards.

## Configuration

`config/pnshop.php` in a new shop holds only your overrides; every option and its default lives in the core package. Shops whose `config/pnshop.php` is a full copy keep working: their values win, and options added by updates now arrive too. You may trim the copy down to the values you changed.

## For developers

- **New services:** `PnShop\Catalog\VariantService` (save, delete, generate), `PnShop\Sales\Checkout\DeliveryQuote`, `PnShop\Customer\Registration`, and `CustomerAddress::makeDefault()`.
- **`PnShop\Sales\ManualStateChanges`:** which state changes staff may set by hand.
- **`PaymentService::apply()`:** idempotent and never moves a settled payment backwards. Gateway plugins can call it from webhooks without their own duplicate checks.
- **Migrations:** date your own migrations after the newest core one (`2026_10_13_*`); see [core modules](../development/core-modules.md#migrations-and-their-order).
